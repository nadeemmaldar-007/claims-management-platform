# AI Journal

## Purpose

This journal records how AI assistance was used to build **claims-management-platform**: what was asked, what was run, what went wrong and how it was fixed. It is written for the examiner and for the developer. Entries state only what actually happened; commands are the ones really run and results are the ones really seen.

## Tools used

- **Claude Code** (model `claude-sonnet-5-5`), working directly in the project folder, which is open in **IntelliJ IDEA Community Edition 2025.2.5** on Windows 11.
- Shell used by the assistant: Windows PowerShell 5.1, with Git Bash used for POSIX tools such as `sed`.
- Build tooling: Maven Wrapper 3.3.4 configured for Apache Maven 3.9.11 (created in prompt 1, stage 3), JDK 21.

## Developer's role

The developer supplies the seven prompt files (kept verbatim in `prompts/`), confirms the environment facts, reviews the output, and decides anything the prompts mark as "stop and ask". The assistant carries out the stages, runs the commands and reports real results. The developer remains responsible for reviewing the design, the code and the claims made in the documents.

## Decisions and reasons

- The JDK 21 path was taken from IntelliJ's own SDK registry rather than guessed, so the command line uses the same JDK as the IDE.
- The IntelliJ-generated `.gitignore` was replaced by the prompt's list, because the prompt requires specific entries (`data/`, `.env`, `.claude/settings.local.json`) and requires `.claude/ai-journal.md` and the Maven wrapper files to stay tracked.
- Prompt 2: repository tests run on their own in-memory database (`claims_repo_test`) and roll back every test, so the reference data stays exactly as migration V6 left it. Without this, rows committed by the Spring Boot tests of later prompts would break the assertion that the counters start at 10001. The cost is that the repository tests never see rows from other test classes, which is the intent.
- Prompt 2: the commit order was migrations, entities and repositories, seeder, tests. The prompt lists migrations, entities and tests, and puts the seeder commit in its own stage; the seeder needs the entities, so committing it earlier would have left a commit that does not build.
- Prompt 2: the identity to market dependency was implemented as the prompt's repository method requires and was documented instead of being worked around. A workaround (a plain `marketId` column in `AppUser`) would still not remove the dependency, because registration and login both resolve market codes.
- Prompt 2: the enum drift guard covers all 12 enums with a CHECK constraint, not only the six the prompt names, because the cost per enum is a few lines and the failure it prevents is the same.
- Prompt 3: the role is a required enum query parameter of the login endpoint, as the prompt specifies, so that Swagger UI renders a dropdown. ## Limitations

Known so far (to be extended as the project progresses; the Docker files, simulated systems, static rates and single relay instance are still to come):

- Tests run on H2 in PostgreSQL mode, so PostgreSQL-only behaviour is checked by hand. In prompt 2 that meant one real start against PostgreSQL 17.6 and queries on the result; no automated test targets PostgreSQL.
- The pessimistic lock on the claim number counter was tested for query correctness and for the increment inside one transaction. Two real threads competing for it have not been tested yet.
- The Mermaid diagrams in `docs/` have never been rendered, because Node.js and Python are not installed on this machine.
- The seeder takes the current date from `LocalDate.now(ZoneOffset.UTC)`; there is no injectable `Clock` yet.
- The application was started twice with `Stop-Process`, a forced stop, so the graceful-shutdown path was not exercised.
- No Docker command was run, and the Docker files do not exist yet.
- There is no login throttling and no account lockout, so passwords can be guessed at the speed of one BCrypt check per request. Nothing in this prompt addresses that.
- There are no refresh tokens: a token is valid for 120 minutes and the user logs in again afterwards.
- The role in a token is trusted until it expires; only deletion and deactivation take effect at once.
- Every protected request costs one extra database query (the account check), plus one more for the services that load the current user.
- Spring validates a request body before the role check, so a caller without the role sees a 400 instead of a 403 when the body is invalid.
- The security tests run on H2 with MockMvc; the real servlet container, TLS and a reverse proxy were not involved. The live smoke run covered the real container and PostgreSQL once, by hand.
- The smoke script is not part of `mvn verify`; it has to be run against a running instance, and it leaves two users in the database per run.
