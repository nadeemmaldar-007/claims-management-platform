# AI Journal

## Purpose

This journal records how AI assistance was used to build **claims-management-platform**: what was asked, what was run, what went wrong and how it was fixed. It is written for the examiner and for the developer. Entries state only what actually happened; commands are the ones really run and results are the ones really seen.

## Tools used

- **Claude Code** (model `claude-sonnet-5-5`), working directly in the project folder, which is open in **IntelliJ IDEA Community Edition 2025.2.5** on Windows 11.
- Shell used by the assistant: Windows PowerShell 5.1, with Git Bash used for POSIX tools such as `sed`.
- Build tooling: Maven Wrapper 3.3.4 configured for Apache Maven 3.9.11 (created in prompt 1, stage 3), JDK 21.

## Developer's role

The developer supplies the prompt files (kept verbatim in `prompts/`; seven were planned, six after the amendment of prompt 5), confirms the environment facts, reviews the output, and decides anything the prompts mark as "stop and ask". The assistant carries out the stages, runs the commands and reports real results. The developer remains responsible for reviewing the design, the code and the claims made in the documents.

## Decisions and reasons

- The JDK 21 path was taken from IntelliJ's own SDK registry rather than guessed, so the command line uses the same JDK as the IDE.
- The IntelliJ-generated `.gitignore` was replaced by the prompt's list, because the prompt requires specific entries (`data/`, `.env`, `.claude/settings.local.json`) and requires `.claude/ai-journal.md` and the Maven wrapper files to stay tracked.
- Prompt 2: repository tests run on their own in-memory database (`claims_repo_test`) and roll back every test, so the reference data stays exactly as migration V6 left it. Without this, rows committed by the Spring Boot tests of later prompts would break the assertion that the counters start at 10001. The cost is that the repository tests never see rows from other test classes, which is the intent.
- Prompt 2: the commit order was migrations, entities and repositories, seeder, tests. The prompt lists migrations, entities and tests, and puts the seeder commit in its own stage; the seeder needs the entities, so committing it earlier would have left a commit that does not build.
- Prompt 2: the identity to market dependency was implemented as the prompt's repository method requires and was documented instead of being worked around. A workaround (a plain `marketId` column in `AppUser`) would still not remove the dependency, because registration and login both resolve market codes.
- Prompt 2: the enum drift guard covers all 12 enums with a CHECK constraint, not only the six the prompt names, because the cost per enum is a few lines and the failure it prevents is the same.
- Prompt 3: the role is a required enum query parameter of the login endpoint, as the prompt specifies, so that Swagger UI renders a dropdown. The role stored on the account stays authoritative; the parameter is only compared with it. Every login failure returns the same 401 and message so account existence is not revealed.
- Prompt 3: the token's account is checked on every request through a port (`ActiveAccountChecker`) that `security` declares and `identity` implements. This keeps `security` free of any feature module and is what makes the spec's "loaded on each request" true for every endpoint, not only the ones that call `CurrentUserService`. It costs one existence query per request.
- Prompt 3: `config.ClockConfig` was created in stage 1 and not stage 2, because the exception handler needs a `Clock` and a commit without the bean would have broken every Spring Boot test.
- Prompt 3: account creation exists once, in `UserService.createAccount`; registration and staff creation both call it, so the duplicate, market and password rules cannot drift apart.
- Prompt 3: the "validation before authorization" behaviour was accepted and documented instead of being worked around, because fixing it needs the role rules duplicated in the filter chain. A test records it.
- Prompt 3: the service layer builds the DTO records that live in `api.dto`, as the prompt places them, so `service` depends on `api.dto`. The architecture tests of prompts 4 to 6 must allow that.
- Prompt 4: the services flush the claim first and write the timeline entry and the event afterwards, although the prompt lists the flush last, so that a lost version race leaves no timeline entry and no event behind (the transaction rolls back either way, but the order makes the intent visible and the exception arises inside the method).
- Prompt 4: the two business rules on a named field that have no error code of their own (an unsuitable `officerUserId` on assign, an `approvedAmount` above the recommended payout) answer 422 with the existing code `VALIDATION_FAILED` and a message that names the field. The alternative, a new code, would have changed the list of 20 codes that the specification fixes and a test pins.
- Prompt 4: the reason an officer gives for an escalation is shown to staff and replaced by a neutral text for the claimant in `ClaimMapper`. The timeline entry type decides visibility (ESCALATED is PUBLIC), so the replacement is done when the entry is read; the remarks are still stored.
- Prompt 4: creating an information request answers 201 with the request (the client needs its id to answer or cancel it), although the prompt says that actions return the claim; answering and cancelling return the claim.
- Prompt 4: two named exceptions to the layer rules instead of moving 23 records out of `api` ([ADR 0014](../docs/adr/0014-api-records-and-kernel-api-in-the-layer-rules.md)). The specification and `docs/02-architecture.md` already said that services use `api.dto`; the rule in the prompt could not hold together with that.
- Prompt 4: test and smoke data use days inside the year the seeded policies cover, not the last 1500 days of the prompt, because an older day is refused by the policy check; new claimants get policies that start six years back.
- Prompt 5: the payment status is `COMPLETED`, not the `PAID` of the prompt, because the CHECK constraint of migration V4 allows only `INITIATED`, `COMPLETED` and `FAILED` and the migrations are locked. A new migration only to rename a status would have bought nothing.
- Prompt 5: the gateway is called before the claim changes state, and its record is written in `REQUIRES_NEW`. A refused or failed call leaves the claim `APPROVED` and writes nothing else; a payment that did succeed stays recorded when the settlement fails afterwards, and the retry finds it by claim number and reuses its reference. The alternative (one transaction around both) would lose the proof that money moved.
- Prompt 5: a notification is built from the event payload alone, so `notification` depends on `shared` and `identity` and never on `claim`. The cost is that the events carry the amounts, the currency and the market, which the write side of prompt 4 already put there.
- Prompt 5: a failed event stays `PENDING` with a later `next_attempt_at`; the schema has no `RETRY` status, and a fifth failure makes it `FAILED`. The stored error is the exception class and message, never the payload.
- Prompt 5: reports are folded in memory from one scoped query instead of by SQL aggregates, so the arithmetic (aging bands, exposure by status, approval rate, rounding) is plain Java that is unit-tested without a database. The cost is that the work grows with the claims in scope; fine for a demo, not for a large portfolio.
- Prompt 5: an officer who names another market in a report gets an empty report, not a 403 or a 404: the scope is "own market" and the claims in it are none. An unknown market code is a 400. Documented in `NOTES.md` and `docs/04-api-design.md`; a different answer would be a small change in `ReportingService`.
- Prompt 5: the exchange rates are converted per figure and rounded half-up to two decimals, so a total is the sum of rounded figures and every row adds up on screen. Every exposure response states `STATIC_ILLUSTRATIVE`.
- Prompt 5: the layer rules got a third named exception (`bootstrap` may use `claim.api.dto`) instead of a seeder that bypasses the services with SQL. Sample claims that skip the services would have no timeline entries and no outbox events.
- Prompt 5: tests that run the relay park the older pending outbox rows first (`OutboxBacklog.park`), because the shared test database holds events from every other test class and a batch would otherwise deliver other tests' events.

## Limitations

Known so far (to be extended as the project progresses; the Docker files, simulated systems, static rates and single relay instance are still to come):

- Tests run on H2 in PostgreSQL mode, so PostgreSQL-only behaviour is checked by hand. In prompt 2 that meant one real start against PostgreSQL 17.6 and queries on the result; no automated test targets PostgreSQL.
- The pessimistic lock on the claim number counter was tested for query correctness and for the increment inside one transaction. Two real threads competing for it have not been tested yet.
- The Mermaid diagrams in `docs/` have never been rendered, because Node.js and Python are not installed on this machine.
- The seeder takes the current date from `LocalDate.now(ZoneOffset.UTC)`; there is no injectable `Clock` yet.
- The application was started twice with `Stop-Process`, a forced stop, so the graceful-shutdown path was not exercised.
- No Docker command was run, and the Docker files do not exist yet.
- There is no login throttling and no account lockout, so passwords can be guessed at the speed of one BCrypt check per request. Nothing in this prompt addresses that.
- There are no refresh tokens: a token is valid for 120 minutes and the user logs in again afterwards.
- The role in a token is trusted until it expires; only deletion and deactivation take effect at once.
- Every protected request costs one extra database query (the account check), plus one more for the services that load the current user.
- Spring validates a request body before the role check, so a caller without the role sees a 400 instead of a 403 when the body is invalid.
- The security tests run on H2 with MockMvc; the real servlet container, TLS and a reverse proxy were not involved. The live smoke run covered the real container and PostgreSQL once, by hand.
- The smoke script is not part of `mvn verify`; it has to be run against a running instance, and it leaves two users in the database per run.
- The duplicate-claim check is a read followed by an insert, so two identical submissions at exactly the same moment without an `Idempotency-Key` can both pass it. With a key the second request fails on the unique key and rolls back.
- The races (two and six simultaneous pick-ups) were tested with real threads on H2 only. On PostgreSQL the smoke script ran sequentially, so the version check and the counter lock under real contention on PostgreSQL were not exercised.
- The tests for the claims core check behaviour through the API; the outbox rows are written, but nothing delivers them until prompt 5, so no notification exists yet.
- Seeded policies cover one year each side of the seeding date; a claim on them needs an incident day inside that year.
- The architecture rules are the first of two sets; prompt 6 completes them, and the two exceptions in ADR 0014 stay until the records move or the ADR is retired.
- The defect check of the tests was stopped before it finished (14 of the 15 completed defects were caught; two never ran), so the strength of the tests is partly measured, not proven.
- Added in prompt 5: the architecture rules are now complete (35 rules, three named exceptions in ADR 0014) and the 75 percent line-coverage gate is enforced by `verify`; the last measured coverage was 95.58 percent. Coverage says which lines ran, not that every behaviour is checked.
- The outbox relay was tested with `processBatch()` called directly and with real threads on H2. On PostgreSQL it ran only through the smoke script (56 events delivered, none failed), one instance, sequentially; two relay instances, the lock behaviour and a failing handler on PostgreSQL were not exercised.
- Notification delivery is a log line with a masked address; no email, SMS or push exists, and nothing retries a channel failure (the handler swallows it and logs).
- The simulated payment gateway proves the transaction design (idempotency, retry, rollback of the claim), not a real gateway's behaviour (timeouts, partial failures, callbacks, reconciliation).
- The report figures were checked by unit tests of the calculators and by API tests with known data; they were not compared with an independent source. Aging is in whole days and the period filter of the performance report is by UTC day.
- The smoke script's notification step polls for up to 15 seconds; a slower relay would make it fail even if the application is correct.
