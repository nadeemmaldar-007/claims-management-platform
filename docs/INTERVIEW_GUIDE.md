# Interview Guide

For the person who built or presents the project. Every statement here matches the code in this repository; where something is simulated, limited or not tested, the guide says so, because the honest answer is also the strongest one. Real figures come from the final verification: 1396 tests (0 failures) and 95.58 percent line coverage at the last full run, 35 architecture rules, and a smoke script of 165 steps that passed twice against a fresh PostgreSQL 17 database. See [README.md](../README.md) for how to run it.

## 1. The two-minute pitch

An APAC property and casualty insurer handles motor and property claims in six markets by phone and email. Claimants cannot see where a claim stands, claims staff work from shared inboxes, and managers cannot see outstanding claims or liability exposure without asking each team for a spreadsheet.

I built the backend that replaces that. A claimant submits a first notice of loss against their own policy. Officers see a queue for their market, pick a claim up, assess it (the system computes deductible and payout), ask the claimant for information, and approve within their market's limit or escalate to a manager. Approved claims are settled through a payment gateway port. Every step writes an audit entry, and claimants are notified of what happens. Managers read live exposure per market and in one base currency.

Three design choices carry the project. It is a **modular monolith**: one deployable with eleven modules whose dependencies are written down and enforced by 35 ArchUnit rules, so the structure cannot drift. State changes and their events commit together through a **transactional outbox**, and a relay delivers them to idempotent consumers, so there is no broker to run and no lost or phantom event. And every failure mode I could name has a test: races on pick-up with real threads, a payment gateway that fails, a retried submission, a role that is not allowed.

What is simulated, said plainly: the policy system (a local snapshot), the payment gateway, email (a log line) and the exchange rates (static and labelled illustrative). Docker files are provided but could not be run on my machine.

## 2. Five-minute Swagger demo

Setup before the demo: PostgreSQL 17 with an empty `claims_db`, start the application (see the README), open <http://localhost:8080/swagger-ui/index.html>. On a fresh database the seeder has created four sample claims (`CLM-10001`, `CLM-10002`, `CLP-10001`, `CLP-10002`) and the next new claims are `CLM-10003` and `CLP-10003`. The demo uses `CLM-10003`, so run it on a fresh database; otherwise use the number the submission returns.

Each step needs the token of the account named in it: `POST /api/v1/auth/login` with the role from the dropdown, copy `accessToken`, click *Authorize*, paste the token only. Swapping accounts is the slowest part; keep two browser tabs open (one for the claimant, one for staff) if time is short.

## 3. Architecture walkthrough

Walk it top down, with [02-architecture.md](02-architecture.md) and the diagrams in the README open.

1. **Shape.** One Spring Boot application, base package `com.apac.claims`, eleven first-level packages as modules. A claim change, its timeline entry and its outbox row are one database transaction, which a modular monolith gives for free and microservices would turn into a distributed problem.
2. **Modules and rules.** `shared` is the kernel, `config` and `security` are infrastructure, `identity` and `market` are reference domains, `claim` is the core, `policy` and `integration` implement ports that `claim` owns, `notification` and `reporting` are consumers, `bootstrap` wires and seeds. The dependency table is in the spec, in the README, and as data in `ModuleDependencyRulesTest`, which fails the build on any other dependency or any cycle.
3. **Layers inside a module.** `api` (controllers and request and response records), `service` (use cases, one public method per transaction, and the ports), `domain` (entities, rules, repositories), `infrastructure` (adapters). Entities never leave the service layer; services map them to records inside the transaction, which is why `open-in-view` is off. [ADR 0014](adr/0014-api-records-and-kernel-api-in-the-layer-rules.md) records the three exceptions to the layer rules and why the alternative (moving 23 records) was not worth it.
4. **A request.** Correlation id filter, then the JWT filter chain (signature, issuer, expiry, then a check that the account still exists and is active), then `@PreAuthorize` for the role, then the service for the scope rules. A failure at any point becomes the same RFC 7807 body through one `GlobalExceptionHandler`.
5. **Events.** The service raises an event through `DomainEventPublisher`; the adapter in `integration` requires a running transaction and writes a `PENDING` row. The scheduled relay takes due rows oldest first, calls every `DomainEventHandler` in a transaction per event, and marks the row `PROCESSED`, or records the attempt and a doubling delay and finally `FAILED`. The only consumer today is notifications, which is idempotent through a unique `(source_event_id, recipient_id)`.
6. **Ports.** `PolicyLookup`, `PaymentGateway` and `NotificationChannel` are interfaces owned by the module that needs them. Each has one adapter: a database snapshot, a simulated gateway, a logging channel. Replacing one changes one class.
7. **Reporting.** Read only. One query loads the claims in scope, plain calculators add them up with a fixed clock in tests, nothing is cached.
8. **Data.** Flyway `V1` to `V6`, Hibernate `validate`, portable SQL so the same migrations run on PostgreSQL 17 and on H2 in the tests. Enums are strings with `CHECK` constraints; business invariants (unique claim number, unique idempotency key, unique notification per event and recipient, one payment per claim) are constraints, not only code.

## 4. Fifteen likely questions

**1. How are the module boundaries kept?**
By tests, not by discipline. `ModuleDependencyRulesTest` computes, from the real classes, which modules each module depends on and compares that with the table from the specification; it also checks for cycles, that no module uses another's `api` or `infrastructure` package, that `claim` never depends on `policy`, `notification`, `reporting` or `integration`, that `notification` never depends on `claim`, and that `reporting` never writes. `LayerRulesTest` and `CodingRulesTest` cover the layers and the conventions: 35 rules in all, each with a control test showing it can fail. There are three named exceptions, written into the rules and into ADR 0014. The honest limit: it is one Maven module, so the compiler does not stop anyone; the tests do.

**2. Why an outbox and not a message broker?**
There is one deployable and one database, so the only thing a broker would buy now is more infrastructure. The outbox gives what matters: an event exists if and only if its state change committed, because they are in the same transaction. The relay is the seam: replace its in-process dispatch with a publish to a topic, mark the row processed after the broker acknowledges, and the services keep calling `DomainEventPublisher` unchanged. The costs are real: delivery is at least once, so consumers must be idempotent; the relay is a single instance (two would deliver a row twice, and scaling out needs `FOR UPDATE SKIP LOCKED`); order is not guaranteed after a retry; and rows are never purged in this version. I tested the relay by calling its one-batch method directly, including a failing handler, the backoff and `FAILED`; I did not test it on PostgreSQL under contention.

**3. How is idempotency handled?**
In three places, each with a different key. Claim submission: an optional `Idempotency-Key` header, unique per user in `idempotency_keys`; a repeat returns the original claim with `200` and `Idempotent-Replay: true`. If two identical requests arrive at the same instant, the second fails on the unique key, rolls back with its claim number and gets a 409; a retry then receives the replay. Notifications: a unique `(source_event_id, recipient_id)`, checked first, with the insert in its own transaction so a duplicate cannot spoil the relay's transaction. Payments: the gateway adapter is idempotent by claim number through `payment_instructions`, so a retry returns the same reference. Without a key, submission is protected only by a business check (same policy, incident date and type), which is a read followed by an insert, so two simultaneous keyless requests can both pass it. The key is the safe way to retry.

**4. How do you handle concurrency on pick-up and on claim numbers?**
Pick-up uses optimistic locking: `Claim` has a `@Version`, the service flushes inside the method and translates the lock failure to `409 CLAIM_ALREADY_ASSIGNED`. Tests fire real threads at one claim, two and then six at once, and expect one success. Claim numbers come from a counter row read with a pessimistic write lock inside the same transaction as the claim insert, taken only after all validation has passed, so a refused submission uses no number and a rollback leaves no gap. The limit: the thread tests ran on H2. On PostgreSQL the smoke script ran sequentially, so the lock under real contention there was not exercised.

**5. Why 404 and not 403 for another user's claim?**
A 403 tells the caller the claim exists. Claimants see only their own claims and officers only their market, so anything outside the scope answers 404, the same as an unknown number. A 403 is used where the caller can see the claim but may not act: a claimant or a non-assignee officer trying to assess or approve it, or an officer calling a manager-only endpoint. The cost is that a caller cannot tell "not yours" from "not there", which is the point.

**6. What is the security design, and where does it stop?**
Stateless JWT, HS256 with a shared secret of at least 32 bytes (a shorter one stops the application at start-up), issuer and expiry validated, BCrypt passwords. The role is chosen at login as a query parameter so Swagger shows a dropdown, but the role stored on the account is authoritative; the parameter is only compared with it. Every login failure returns the same 401, so account existence is not revealed. After the signature check, every request also asks whether the account still exists and is active, so a deactivation takes effect at once. Limits, stated rather than hidden: no login throttling or lockout, no refresh tokens, no token revocation list, a role change applies only at the next login, the demo accounts have documented passwords, and Spring validates a request body before the role check, so a caller without the role who sends an invalid body sees a 400 instead of a 403. A test records that behaviour.

**7. How is currency handled?**
Each market has one currency and a claim takes its claimant's market and currency, so there are no cross-currency claims. Decimal places follow the currency (JPY 0, others 2) and are enforced by `MoneyRules`. The approval limit is per market in local currency. For managers, exposure is also shown in USD using static rates in the configuration, converted figure by figure and rounded half up, and every response says `STATIC_ILLUSTRATIVE`. Totals across markets exist only in USD. The rates are not accounting figures, and the application refuses to start if a market's currency has no rate.

**8. How are the reports computed, and what is their limit?**
Live, on every call. One query loads the claims in the caller's scope (an officer's market, or all for a manager) and plain Java calculators add them up: exposure, aging bands (0-2, 3-7, 8-14, 15+ days), workload per officer, performance per officer for a period. The arithmetic is unit-tested with hand-made data and a fixed clock, and the API tests move the figures by driving claims through their states. The limit is scale: the work grows with the number of claims in scope. For a very large portfolio the next step is SQL aggregation or a read model. Another choice worth knowing: an officer who asks for another market's report gets an empty report, not an error.

**9. What is simulated?**
The policy administration system (a table of policies behind the `PolicyLookup` port, which a manager can maintain through `PUT /policies/{n}`), the payment gateway (an idempotent simulated adapter that can be switched to fail with `app.integration.payment.simulate-failure`), email (a logging channel that writes a masked address and never fails the handler), and the exchange rates. Nothing real is called. The payment test proves the transaction design: gateway first, claim state only after it succeeds, a failure leaves the claim APPROVED and writes nothing, a retry reuses the stored reference. It does not prove how a real gateway behaves with timeouts or callbacks.

**10. What is the testing strategy?**
All tests run on H2 in PostgreSQL mode with the same Flyway migrations, so `mvnw -B clean verify` needs no Docker and no database: unit tests for rules, repository tests for constraints, integration tests through MockMvc and the real security chain for journeys and the error contract, and the ArchUnit rules. Gates: green build, 75 percent line coverage by JaCoCo (95.58 percent measured), more than 80 test methods (there are 878), and a contract test that the committed OpenAPI file and the live document have the same paths and methods. Outside Maven, a smoke script drives the running application on real PostgreSQL. What is not tested: the Docker files (never run), PostgreSQL-only behaviour under contention, several relay instances, load, and real external systems.

**11. How are the six markets modelled?**
As data, not code: a `markets` table with country, currency and escalation threshold, created by migration `V6`. Officers and claimants belong to a market; managers have none. A claim copies its claimant's market and currency, and the policy must be in the same market (`POLICY_MARKET_MISMATCH`). Scope follows the market: an officer sees the claims, queue, workload and performance of their own market, and a manager sees all. The six thresholds are in local currency and are roughly comparable in value. A seventh market would be a row in a migration plus a rate in the configuration, and a user to staff it.

**12. How is error handling designed?**
One contract for everything: RFC 7807 with a machine-readable `code` (20 of them, fixed by a test), a `timestamp` and a `correlationId` that is also in the response header and the log lines. One `GlobalExceptionHandler` turns every business exception into its status; validation errors list the fields without echoing values. `AccessDeniedException` is handled explicitly, because the catch-all would otherwise turn a 403 into a 500. The security filters write the same shape for 401 and 403. The status policy is 400 for a bad request, 422 for a business rule, 409 for state and duplicates, 502 for the payment gateway, and a generic 500 whose stack trace goes only to the log. Two rules without a dedicated code (an unsuitable assignee, an approved amount above the payout) use `VALIDATION_FAILED` with 422.

**13. What would you build next?**
In order of value: real adapters behind the existing ports (policy system, payment gateway, email or SMS); a broker behind the relay if a second consumer appears, and `SKIP LOCKED` if the relay must run in more than one instance; login throttling, refresh tokens and token revocation; attachments for information responses through a storage port; reports in SQL or a read model; claimant withdrawal and appeals; PostgreSQL-based integration tests in a CI that has Docker, to cover what H2 cannot.

**14. What would you change for production?**
Take the JWT secret from a secret store and consider asymmetric keys; remove the demo accounts and passwords; run behind TLS; add metrics, tracing and alerting (only health is exposed now); purge old outbox rows and idempotency keys and decide a retention period; add indexes on the foreign-key columns that are queried (PostgreSQL does not create them, and none were added because the data volume is small); run the relay safely in more than one instance; add rate limiting; set up database backups; replace the static rates with a feed or drop base-currency totals; and exercise the Docker packaging in a pipeline, which has not been run.

**15. How was AI used?**
Claude Code worked in the project folder from six staged prompts, which are saved verbatim in `prompts/`. Each prompt had stages with commands to run, and every claim of success has a command and output recorded in `.claude/ai-journal.md`. The journal also records what went wrong: for example an unrequested defect check of the tests in prompt 4 that took too long and was stopped, a timestamp-precision mismatch (nanoseconds against the database's microseconds) that was a real defect and was fixed in the code, one test that needed a documented one-microsecond tolerance because H2 rounds timestamps, a payment status in a prompt that the schema does not allow (`PAID` against `COMPLETED`), and statements in documents that were corrected because they had not been measured. I treat the AI as a fast, literal engineer: the architecture rules, the contract test and the smoke script exist so that its output is checked by something other than its own word, and the developer is responsible for reviewing the design, the specification amendments and the exceptions that were accepted.
