# 03. Data Model

Status: **Implemented** in prompt 2 and used unchanged by prompts 3 to 6. Migrations `V1` to `V6`, the entities and the repositories are built and were checked on H2 in PostgreSQL mode and on PostgreSQL 17.6 (section 7 lists what was verified and where the build differs from the first draft of this document; section 9 records the final run on a fresh database).

## 1. Conventions

- Flyway migrations own the schema. Hibernate runs with `ddl-auto: validate`, so a mismatch between an entity and a table fails startup and fails the repository tests.
- Enums are stored as `VARCHAR` strings with `CHECK` constraints, and mapped with `@Enumerated(EnumType.STRING)`.
- Primary keys are `BIGINT GENERATED BY DEFAULT AS IDENTITY`, except `claim_counters` (key `claim_type`) and `outbox_events` (key is the event id, `VARCHAR(36)`).
- Money is `NUMERIC(19,2)`. Timestamps are `TIMESTAMP WITH TIME ZONE` (Java `Instant`). Dates are `DATE` (`LocalDate`). Booleans are `BOOLEAN`.
- Names avoid reserved words (`read`, `user`, `value`, `year`, `order`); the read flag is `read_flag`, the users table is `app_users`.
- Entities are plain classes with explicit getters and setters and a protected no-argument constructor. Associations are `LAZY`; `spring.jpa.open-in-view` is `false`. `Claim` has `@Version`. Timestamps are set in `@PrePersist` and `@PreUpdate`.

**`claim_assessments`**: internal assessments; several are allowed and the latest counts.

Columns: `id`, `claim_id` (FK), `assessed_by_id` (FK), `assessed_loss_amount`, `deductible_applied`, `recommended_payout`, `coverage_confirmed`, `recommendation` (`APPROVE`, `REJECT`, `ESCALATE`), `notes` (`VARCHAR(2000)`, nullable: the API decides whether notes are required), `created_at`.

**`information_requests`**: questions to the claimant.

Columns: `id`, `claim_id` (FK), `requested_by_id` (FK), `question` (`VARCHAR(1000)`), `due_at`, `status` (`OPEN`, `RESPONDED`, `CANCELLED`), `response_text` (`VARCHAR(2000)`), `responded_by_id` (FK), `responded_at`, `created_at`. "Overdue" is computed when read (`OPEN` and `due_at` in the past), not stored.

**`claim_timeline_entries`**: append-only audit trail.

Columns: `id`, `claim_id` (FK), `entry_type` (`SUBMITTED`, `ASSIGNED`, `REASSIGNED`, `ASSESSMENT_RECORDED`, `INFORMATION_REQUESTED`, `INFORMATION_PROVIDED`, `INFORMATION_REQUEST_CANCELLED`, `ESCALATED`, `APPROVED`, `REJECTED`, `SETTLED`), `from_status`, `to_status` (both nullable, each with a CHECK against the seven claim statuses), `actor_user_id` (`VARCHAR(30)`, a value rather than a foreign key), `message` (`VARCHAR(1000)`), `visibility` (`PUBLIC` or `INTERNAL`), `occurred_at`. `ASSESSMENT_RECORDED` and `REASSIGNED` are `INTERNAL`; all others are `PUBLIC`. Claimants only ever read `PUBLIC` entries.

**`idempotency_keys`**: remembers which claim a submission key created.

Columns: `id`, `user_id` (FK), `idempotency_key` (`VARCHAR(64)`), `claim_number`, `created_at`. Constraint: unique `(user_id, idempotency_key)`.

## 4. Rules for Flyway migrations

1. Files are named `V<n>__<description>.sql` in `src/main/resources/db/migration`, numbered without gaps.
2. A migration that has been applied or committed is never edited. A change to the schema is a new version.
3. SQL is portable between PostgreSQL 17 and H2 in PostgreSQL mode: no `TEXT`, `JSONB`, sequences, partial indexes or vendor functions. Use `VARCHAR(n)`, `NUMERIC(19,2)`, `TIMESTAMP WITH TIME ZONE`, identity columns and plain `CHECK` constraints.
4. Every enum column has a `CHECK` constraint listing its values, so the database rejects an out-of-range value even if the application has a bug.
5. Constraints that express business invariants (unique claim number, unique idempotency key, unique notification per event and recipient) are in the schema, not only in code.
6. Reference data lives in migrations; demo data lives in `DataInitializer`.
7. `ddl-auto` stays `validate`. An entity change without a migration must fail a test.
8. Rollbacks are not scripted. A wrong migration is fixed forward with a new version.

## 5. Data ownership per module

| Module | Owns tables | Notes |
|---|---|---|
| `market` | `markets` | Reference data |
| `identity` | `app_users` | Foreign key to `markets` (`market_id`), which is why `identity` depends on `market` (see [02-architecture.md](02-architecture.md)) |
| `policy` | `policies` | Foreign keys to `markets` and `app_users` only |
| `claim` | `claim_counters`, `claims`, `claim_assessments`, `information_requests`, `claim_timeline_entries`, `idempotency_keys` | Refers to a policy by number; foreign keys to `markets` and `app_users` only |
| `integration` | `outbox_events`, `payment_instructions` | Refers to claims by value |
| `notification` | `notifications` | Foreign key to `app_users` only |
| `reporting` | none | Read side; reads claim data through the `claim` module's `service` and `domain` types |
| `security`, `config`, `shared`, `bootstrap` | none | |

Rule: **no foreign key crosses a module boundary except to identity (`app_users`) and market reference data (`markets`).** Within a module, foreign keys are allowed. Child tables of `claims` are in the same module for that reason.

## 6. Retention and audit notes

- `claim_timeline_entries` is append-only: the application has no update or delete path for it. Together with the decision and settlement columns on `claims` it is the audit record of who did what and when.
- Claims are never deleted by the application. Claimant withdrawal is out of scope.
- Rows in `outbox_events` stay after processing, which is useful for diagnosis. A housekeeping job that purges old `PROCESSED` rows is not built in this version; the retention period is an open question.
- `idempotency_keys` rows are also kept. Purging them after a retention window would be a later task.
- Personal data is limited to name, email and user id. Passwords are BCrypt hashes. Logs carry user ids and claim numbers only.
- Timestamps are stored in UTC (`hibernate.jdbc.time_zone: UTC`).
- The child tables read by `claim_id` (`claim_assessments`, `information_requests`, `claim_timeline_entries`) and `policies.holder_id` are queried by those columns, and PostgreSQL does not index foreign keys automatically. Decision in prompt 2: **no extra index was added**, because the specification lists its indexes exactly and the data volume is small. Adding them later is a new migration if a query plan shows the need.

### Where the build differs from, or adds to, the first draft of this document

- **Naming.** Every constraint and index has an explicit name: `pk_<table>`, `fk_<table>_<column>`, `uq_<table>_<column(s)>`, `ck_<table>_<column>`, `ix_<table>_<columns>`. The check that keeps a non-manager from lacking a market is `ck_app_users_market_required`.
- **Column lengths** (the specification fixes types, not all lengths). Chosen: `markets.code` 2, `currency_code` 3, `country_name` 60; `app_users.user_id` 30, `password_hash` 100, `full_name` 100, `email` 150; `policy_number` 30, `insured_item` 200; `claim_number` 20, `incident_location` 200, `description` 1000, `property_address` 300, `vehicle_*` 50 (registration 20), `police_report_number` 50, `payment_reference` 40; `decision_reason` 40, `decision_remarks` 1000; `notes` 2000, `question` 1000, `response_text` 2000; `outbox_events.id` 36, `aggregate_type` 30, `aggregate_id` 50, `event_type` 50, `payload` 8000, `last_error` 1000; `payment_instructions.reference` 40; `notifications.title` 150, `message` 1000, `source_event_id` 36; `idempotency_key` 64. Enum columns: statuses 30, `entry_type` 40, `decision_reason` 40, others 20 (except `notifications.notification_type`, see below).
- **`notifications.notification_type` is `VARCHAR(30)`, not 20,** because `INFORMATION_REQUESTED` has 21 characters.
- **Nullability.** `claim_assessments.notes` is nullable (see above). `claim_timeline_entries.from_status` and `to_status` are nullable. All other columns not marked optional in the specification are `NOT NULL`, including `outbox_events.next_attempt_at` (initially equal to `occurred_at`).
- **Defaults.** The only database default is `claims.version BIGINT NOT NULL DEFAULT 0`. Timestamps have no default; the entities set them in `@PrePersist` and `@PreUpdate`.
- **Check constraints.** Every enum column has one (rule 4 in section 4), including `claim_timeline_entries.from_status` and `to_status`, `claims.decision_reason` (the rejection reason codes) and `payment_instructions.payment_method`, in addition to `ck_app_users_market_required`. `outbox_events.event_type` has none, because event types are an open list.
- **`OutboxEvent` implements `Persistable<String>`** with a transient "new" flag, because its id is the application-assigned event UUID. A test proves that saving a second new event with the same id fails with a duplicate-key error, which shows an INSERT is issued and not a merge.
- **Claim number counter.** The lock query `ClaimCounterRepository.findForUpdate` (`PESSIMISTIC_WRITE`) is tested for correctness and for the increment inside a transaction on H2. Contention between two real threads is not tested yet; it is first exercised when the claim number generator is built.
- **Dependency.** Because `app_users.market_id` is a foreign key to `markets`, `AppUser` has an association to `Market`, so `identity` depends on `market`. See the clarification in [02-architecture.md](02-architecture.md).

## 8. How the claims core uses the tables (prompt 4)

Prompt 4 changed no migration and no entity column: `V1` to `V6` are untouched. This section records how the code fills the tables.

| Table | What the claims core does |
|---|---|
| `claim_counters` | `ClaimNumberGenerator.next(type)` reads the row of the claim type with a pessimistic write lock (`@Transactional(MANDATORY)`) and increments `next_value`. The number is taken only after every validation of the request has passed, so a refused submission never uses a number. The format is `CLM-<n>` for motor and `CLP-<n>` for property |
| `claims` | A claim is inserted as `SUBMITTED` with the policy figures copied from the policy at that moment (`policy_sum_insured`, `policy_deductible`), the market and currency of the claimant, and the motor or the property columns, never both. Pick-up and assignment set `assigned_officer_id` and `assigned_at` and move the claim to `UNDER_REVIEW`; a reassignment changes both columns and keeps the status. Approval sets `decision_type` `APPROVED`, `decided_by_id`, `decided_at`, `decision_remarks` and `approved_amount`; rejection sets `decision_type` `REJECTED`, `decision_reason` and `decision_remarks`, and leaves `approved_amount` empty. The settlement columns stay empty until the claim is settled (section 9). `version` is managed by Hibernate and is what decides two simultaneous pick-ups |
| `claim_assessments` | One row per assessment, never updated. `deductible_applied` is the claim's `policy_deductible`; `recommended_payout` is computed by the system. The newest row (highest `id`) is the one that counts |
| `information_requests` | `OPEN` on creation with `due_at`; `RESPONDED` with `response_text`, `responded_by_id` and `responded_at`; or `CANCELLED`. Whether a request is overdue is worked out when it is read, from `status` and `due_at`, and is not stored |
| `claim_timeline_entries` | Written only by `TimelineService`, inside the transaction of the change it describes. `from_status` is empty when the status did not change; `to_status` is always filled. `actor_user_id` is the user id of whoever acted. `message` is cut at 1000 characters. Assessments and reassignments are `INTERNAL`, everything else `PUBLIC` |
| `idempotency_keys` | One row per `(user, key)` with the claim number it produced, written in the claim's transaction. A second request with the same key at the same moment fails on the unique constraint and rolls back |
| `outbox_events` | `OutboxDomainEventPublisher` writes one `PENDING` row per event, in the transaction of the state change, with the whole envelope as JSON in `payload` (event id, type, aggregate, time, version, payload; at most 8000 characters). `aggregate_id` is the claim number |

The `claim` module reaches policy data only through the `PolicyLookup` port, so it never reads the `policies` table itself.

## 9. As built: settlement, notifications and the final run (prompts 5 and 6)

No migration changed after prompt 2: `git log` of `src/main/resources/db/migration` shows the six files in one commit and nothing since. This section records how the later prompts fill the tables.

| Table | What the code does |
|---|---|
| `claims` (settlement columns) | `ClaimSettlementService` sets `payment_method`, `payment_reference`, `settled_amount` (the approved amount) and `settled_at` and moves the claim to `SETTLED`, but only after the payment gateway has answered |
| `payment_instructions` | One row per settled claim, written by `SimulatedPaymentGateway` in its own transaction (`REQUIRES_NEW`): unique `claim_number`, `reference` of the form `PAY-` plus 12 upper-case hexadecimal characters, status `COMPLETED`. The CHECK constraint allows `INITIATED`, `COMPLETED` and `FAILED`; a payment that was recorded stays recorded if the claim transaction then rolls back, and a retry finds the row by claim number and returns the same reference |
| `outbox_events` | The relay reads `PENDING` rows whose `next_attempt_at` has passed, oldest first, and sets `PROCESSED` and `processed_at` after every handler succeeded. A failure adds one to `attempts`, stores the exception class and message (never the payload) in `last_error` and moves `next_attempt_at` by 2 to the power of `attempts` seconds; the row stays `PENDING` until `attempts` reaches the maximum (5), then it becomes `FAILED` |
| `notifications` | One row per recipient and event, written by `NotificationEventHandler` from the event payload. The unique `(source_event_id, recipient_id)` makes a second delivery of the same event create nothing; the insert runs in its own transaction so a duplicate cannot spoil the relay's transaction |
