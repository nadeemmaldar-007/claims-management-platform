# ADR 0003: PostgreSQL with Flyway migrations and Hibernate `validate`

- **Status:** Accepted
- **Date:** 2026-10-25

## Context

Claims are financial records that need transactions, constraints and a schema that can be reviewed. The schema must be created identically on a developer machine (PostgreSQL 17), in Docker Compose and in tests (H2 in PostgreSQL mode, [ADR 0012](0012-test-strategy-h2-postgresql-mode.md)). Liquibase is excluded by the project constraints.

## Decision

- **PostgreSQL 17** is the database for local runs and Docker Compose.
- **Flyway** owns the schema: `V1__markets_and_identity.sql` to `V6__reference_data.sql` in `src/main/resources/db/migration`. The PostgreSQL support module (`flyway-database-postgresql`) is included because PostgreSQL 17 requires it.
- **Hibernate `ddl-auto: validate`**, so a mismatch between an entity and the schema fails startup and the repository tests.
- Migrations are written in **portable SQL** that runs on PostgreSQL and on H2 in PostgreSQL mode: no `TEXT`, `JSONB`, sequences, partial indexes or vendor functions.
- Enums are `VARCHAR` with `CHECK` constraints. Money is `NUMERIC(19,2)`. Timestamps are `TIMESTAMP WITH TIME ZONE`. Primary keys are `BIGINT GENERATED BY DEFAULT AS IDENTITY` (exceptions: `claim_counters`, `outbox_events`).
- Applied migrations are never edited; changes are new versions ([03-data-model.md](../03-data-model.md), section 4).
- Reference data (markets, counters) is in migration `V6`; demo data is seeded by `DataInitializer`.

## Alternatives considered

| Alternative | Why not |
|---|---|
| Liquibase | Excluded by the project constraints |
| Hibernate `ddl-auto: update` or `create` | The schema is generated, unreviewable and can drift; no versioned history |
| `schema.sql` / `data.sql` scripts | No versioning or checksums, and no protection against editing history |
| H2 as the runtime database | Not representative of production behaviour |
| Vendor-specific SQL for PostgreSQL only | Would force a real PostgreSQL for tests, which means Docker or a local server |

## Consequences

**Good**
- The schema is versioned, reviewable and reproducible; constraints live in the database as well as in code.
- Entity drift is caught early by `validate`.
- The same migrations are exercised by the tests and by the real database.

**Bad**
- Portable SQL rules out some PostgreSQL features (JSONB, partial indexes), so the outbox payload is a bounded `VARCHAR(8000)`.
- Adding an enum value needs a migration that changes the `CHECK` constraint.
- H2 can accept SQL that PostgreSQL rejects or the reverse; the final verification therefore runs the application on PostgreSQL 17.

## Implementation note (prompt 6)

The migrations `V1` to `V6` were committed once in prompt 2 and never edited afterwards (`git log` of the migration folder shows one commit). In prompt 6 the database `claims_db` was dropped and created again, and the packaged application applied all six migrations to the empty database ("now at version v6") with Hibernate `validate` accepting every entity; the same migrations also run on H2 in all tests. No migration was needed after prompt 2, which suggests that the schema chosen at design time was right, but the verification is limited: tests run on H2, and PostgreSQL 17.6 was exercised by running the application and the smoke script sequentially, not under concurrent load.
